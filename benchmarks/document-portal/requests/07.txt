Request 7 — Keep document revision history

People need to recover an earlier note or description. Keep revisions of title, description, note text and original file bytes/filename. Creation starts revision 1; existing documents at upgrade start from their current state as revision 1. Each successful PATCH that changes title, description or note content creates one next revision. No-op edits, moves and archive/restore create none. Imports start at revision 1. Upload replacement remains out of scope.

People who can read a document can browse/download its history under the same active/archive rules. Only its current personal-library or collection owner can restore a revision, while active. Restore copies it into a new highest-numbered revision, keeping ID and location; restoring the latest also creates a revision. Editors continue editing normally. Client handout links display current content only.

GET /api/documents/{id}/revisions -> [{number,created_by,title,description,filename,kind}], ascending by number. created_by is the contributor's string user ID, or null for unavailable pre-upgrade authorship. GET .../revisions/{number} adds content for notes; GET .../revisions/{number}/download returns revision bytes as attachment. POST .../revisions/{number}/restore -> 200 current document. Add history browsing, revision downloads and owner restoration to the browser. Preserve earlier workflows and data across upgrade/restart.
