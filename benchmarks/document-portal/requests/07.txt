Request 7 — Keep document revision history

People need to recover an earlier note or description without undoing collaboration. Keep immutable revisions of each document's title, description, note content and original file bytes/filename. On creating a document its first revision is number 1; for documents already present at upgrade, retain their current state as revision 1. Each successful PATCH that changes title, description or note content creates exactly one next revision; a no-op PATCH, location move, archive/restore or failed mutation creates none. Imported files begin with revision 1 on completion. Existing upload replacement is still out of scope. Preserve accounts, document IDs, locations and bytes during upgrade.

GET /api/documents/{id}/revisions -> array ordered ascending by number of {number,created_by,title,description,filename,kind}; created_by is the string user ID of the contributor, or null for pre-upgrade history whose contributor is unavailable. GET /api/documents/{id}/revisions/{number} -> the same fields plus content for notes. GET .../{number}/download -> exact revision bytes as an attachment. Access to history follows current document access, including archived-owner-only access. Historical authorship grants no permission. No secret storage paths or password fields appear.

POST /api/documents/{id}/revisions/{number}/restore -> 200 current document: only its current personal or collection owner may restore, and only while active. Restoration copies that revision's metadata/content/bytes into a new highest-numbered revision, keeping document ID and current location. Restoring the current revision also creates a new revision. Editors can create revisions through normal permitted edits but cannot restore history. Archived documents' owner can inspect history/downloads but must restore the document before restoring a revision. Client links continue to show only current content and never expose revision routes; history restoration updates what a still-valid link shows.

Add History to document detail with numbered revision links and contributor, and Download revision and Restore revision on a revision page. Confirm restoration visibly and return to current detail. Keep earlier browser/API flows and the original ordinary Download behavior.
