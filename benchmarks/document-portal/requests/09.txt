Request 9 — Browse a large engagement

Library is getting long. Add optional metadata filters to GET /api/documents and /api/search: kind=note|file and title_prefix (case-insensitive literal prefix). Filters combine with each other, q, collection_id and state; search still returns only active documents. Missing filters retain existing semantics. Invalid kind returns 4xx. Without pagination, responses remain arrays as before.

Opt into pagination with page_size (integer 1–100) and optional cursor. The response then becomes {items:[ordinary summaries],next_cursor:string|null}. Order by document ID ascending using string lexicographic order. First page starts at the beginning; continuation returns IDs strictly greater than the last ID of the previous page, applying current access and filters again. Use an opaque cursor tied to the selected filters, query, state, collection and page size; malformed/tampered cursors and use with different parameters return 4xx. A cursor grants no access and cannot expose another person's metadata. With unchanged data, traversing pages returns every match exactly once. Between requests, revoked/archived documents disappear, newly matching IDs after the cursor may appear, and IDs before it need not reappear; no snapshot guarantee. Persisted data and prior unpaginated clients continue working.

In Library/collection search provide Kind (All, Note, File), Title prefix and Apply filters, plus Next page when another page exists. Preserve selection/export for the currently displayed page. Increase the export maximum from 20 to 100 distinct active IDs; the minimum remains 1 and every selection still succeeds entirely or fails entirely before a successful ZIP response. No background export jobs or streaming architecture is required; preserve manifest format, original bytes and contained unique paths. This supersedes only the old 20-item export cap and adds optional filtering/pagination, not a limit to the old unpaginated listing.
