Request 2 — Project collections and collaboration

Consultants now work together on engagements. Add named project collections and memberships rather than copying files between personal libraries. Keep all existing accounts and documents working. Existing documents remain personal until their owner moves them into a collection. Personal notes/uploads are still supported.

Any logged-in person can create a collection and becomes its owner. The owner can add an already registered person by email as reader or editor, change that person's role, and remove them. The owner cannot be removed or demoted. A reader sees and downloads the collection's documents. An editor additionally creates/uploads documents there and edits existing ones. Only the collection owner deletes collection documents or manages membership. Removing someone takes effect for subsequent requests, including links they already have. People outside the collection cannot see its contents. A document's collection is its source of access rights: its original uploader has no special rights after losing membership. An editor's new document belongs to the collection, not their personal library.

An owner can move one of their personal documents into a collection they own, or move a document in their collection back to their personal library. A move preserves ID, content, bytes and metadata. Other cross-collection moves are out of scope. Collection listing and document detail show where a document belongs and the current user's role. Library now lists personal documents plus documents in collections the user belongs to; give people a way to open only one collection. Add visible collection creation, membership editing, document move and collection-specific note/upload flows. Keep the UI useful without requiring users to copy IDs.

Add these API contracts:
- GET /api/collections -> [{id,name,role}] for current memberships. POST /api/collections {name} -> 201 {id,name,role:'owner'}; nonempty name up to 200 characters.
- GET /api/collections/{id}/members -> [{user_id,email,role}], available to members. PUT /api/collections/{id}/members with {email,role:'reader'|'editor'} adds or changes a member -> 200 member. DELETE /api/collections/{id}/members/{user_id} -> 204. Inaccessible resources/forbidden operations return 403 or 404; owners cannot remove/demote themselves (4xx).
- GET /api/documents?collection_id={id} lists only that collection. Document summaries/details additionally include collection_id (string or null). POST /api/documents and multipart /api/uploads accept optional collection_id. PATCH /api/documents/{id} accepts collection_id as a string or null for the moves described above; title/description/content editing continues to work. Mutation responses remain the same shapes/statuses as before.

Browser additions: Library includes Collections. Its page has a Collection name field and Create collection action, and a link named each collection's name. A collection screen contains its document links, Upload and Create note, plus Members. Members shows each person's email and role; owner uses Member email and Role fields and Save member. Each non-owner member has a group accessible by their email with Remove member. On a document the personal-document owner or current collection owner can choose Location (Personal or a collection name) and Save location. Continue to use the existing form labels/actions for other flows. Show the active location on collection and detail screens. Internal implementation and arrangement remain your choice.
