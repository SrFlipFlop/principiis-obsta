Request 5 — Retry a failed delivery without repeating completed work

When the second tool is down, we should not have to rerun the whole workflow. Add Retry failed run for owners/operators. A retry starts at the failed action and proceeds through previously skipped actions. Earlier successful actions remain completed and are not sent again. A run uses its original input, templates, connection settings and action order even if someone has since edited the workflow or connection.

Keep the run ID and each action's original delivery_id. A retry of an uncertain delivery uses the same body and ID, matching the delivery service's existing repeat-delivery contract. Every explicit retry gets a new numbered attempt record, including its failures, responses and timestamps. The initial execution is attempt 1. On restart, finalize any interrupted attempt as failed using its recorded completed action results, a failure/error for the first unfinished or uncertain action and skipped results for later actions. Preserve whatever response evidence was recorded; unknown response status is null. Set finished_at to recovery time and retain an interruption error so it is distinguishable from an ordinary completed failure. Do not mark uncertain delivery succeeded or resume it automatically. Recovery consumes no additional retry: a subsequent explicit retry starts the next numbered attempt under the existing bound. Reject retry on a succeeded run or while execution is already underway. Allow at most three retries per run. This is an application feature limit, unrelated to external development tools.

POST /api/runs/{id}/retry -> 201 updated completed run. GET run details adds attempts:[{number,started_at,finished_at,status,actions}], with the same per-action result shape. Keep prior attempt records immutable; the top-level actions/status show the latest cumulative state. Existing runs become attempt 1 on upgrade. A failed run can be retried only by someone who currently has owner/operator access to its workspace. A retry of a webhook run retains its source/event ID; repeated inbound events still return that same run rather than consuming retries. Add attempt browsing and clear retry feedback to browser run details.
