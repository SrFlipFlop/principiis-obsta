Request 3 — A workflow can notify several tools

We need workflows to send an ordered series of messages. Replace the single connection/template configuration with actions: an ordered array of 1–5 entries {id,label,connection_id,message_template}. Give each action a stable string ID; labels are nonempty, at most 100 characters. All connections belong to the workflow's workspace. Owners can create/edit/reorder actions. The existing template placeholders and run input remain.

Run actions in order. Stop at the first failure; later actions are skipped. A run succeeds only if every action succeeds. Give every action delivery its own distinct delivery_id. Run details show the original action order, labels, rendered messages and delivery outcomes; later workflow/connection edits must not rewrite history. Show the action list and results in the browser.

POST/PATCH workflow accepts actions instead of connection_id/message_template; GET includes actions. Existing workflows become one-action workflows on upgrade, keeping workflow IDs and names. The old single-action format remains accepted as shorthand: creation requires both connection_id and message_template; a PATCH to a one-action workflow may change either while preserving the other. On a multi-action workflow, shorthand PATCH must provide both and replaces the list with one new action. Supplying both formats returns 4xx. PATCH name alone retains actions; supplying actions replaces them as a whole. The app assigns an ID and workflow name as the label for an action created through shorthand. GET /api/runs/{id} adds actions:[{id,label,status,delivery}], where status is succeeded, failed or skipped and delivery has the prior fields or null when skipped. Retain the old delivery field for one-action runs; for multi-action runs it is null. Preserve old run records across upgrade/restart.
