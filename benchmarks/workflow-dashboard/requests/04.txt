Request 4 — Start workflows from incoming events

A few upstream tools can send an event instead of someone pressing Run. Let the owner enable an inbound event URL for each workflow, displayed on its configuration page. Operators/viewers can still use their existing workspace screens. Manual runs continue working.

PUT /api/workflows/{id}/trigger {enabled:boolean} -> {url,enabled}; GET returns that shape to the owner. The URL is POST /hooks/{workflow_id}, receiving JSON {event_id,input:{message,customer}} from an external client. event_id is nonempty, at most 200 characters. An enabled trigger starts the same action sequence as a manual run and returns 201 {run_id,status}. Its run has source:'webhook', initiated_by:null and event_id; manual runs have source:'manual', initiated_by:user ID and event_id:null.

A repeated event_id for this workflow returns 200 with the existing run ID and current status instead of creating another run, even when the input differs or that run failed. A duplicate received while execution is underway waits for that execution's final result. Another workflow may receive the same event ID independently. Disabled triggers return 409 and create neither a run nor a deduplication record. Invalid input returns 4xx without a record. Persist accepted event IDs across restart. After interrupted execution, retain recorded completed actions, mark the first unfinished or uncertain action failed with an interruption error, and mark later actions skipped; the run becomes failed. Retain its original input, configuration, rendered bodies and delivery IDs; do not resume deliveries automatically on startup. New workflows default to disabled. Show incoming runs and their event ID in the browser history.
