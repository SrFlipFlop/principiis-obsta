# Domain documentation

Read root [GLOSSARY.md](../../GLOSSARY.md) and relevant [ADRs](../adr/) before domain or architecture work. This project has one domain context. Use the agreed vocabulary and flag ADR conflicts.

Use `/domain-modeling` when changing terminology or recording a consequential decision. Keep definitions in the glossary, scope and the decisions log in [PROJECT.md](../../PROJECT.md), and rationale in ADRs. Add an ADR only for a hard-to-reverse, non-obvious choice between real alternatives; routine implementation choices belong in engineering documentation.

Research background (charter, protocol, synthesis) is in [docs/research/](../research/README.md). Keep findings, hypotheses, proposals and decisions distinct. Experimental interventions remain separately versioned benchmark artifacts, outside project-wide instructions.
