# Development skills as a later experimental condition

**Checked:** 2026-11-19. **Status:** independent primary-source research for [issue #52](https://github.com/SrFlipFlop/principiis-obsta/issues/52), not an intervention approval or efficacy finding. No skill was installed in an evaluated environment; no model run was made. **Update 2026-11-20:** The owner selected a custom plan–implement–verify workflow as the first design direction. The four-skill bundle below is retained as the earlier research proposal; the current design is [the development-skill condition](../DEVELOPMENT_SKILL_CONDITION.md).

## Scope and sources

The [approved pilot specification](../archive/BASELINE_PILOT_SPEC.md) defines baseline as ordinary Codex with no researcher-added skills, guidance, review or behavioral hooks. It fixes developer requests across compared conditions, separates independent evaluation, and requires machinery/oracle qualification and separate launch approval. [GLOSSARY.md](../../GLOSSARY.md) supplies the condition, task contract, step session and checkpoint terms. The five public [benchmark designs](../../benchmarks/) describe initial builds, later features, changed requirements, preauthored regression reports and behavior-preserving refactors in Python, PHP, C#/.NET, Go and TypeScript/Node. I inspected those public designs and task-file inventory only; no private evaluator material or solution was used. Most designs remain drafts or unqualified, so the final versioned task sequence is not settled.

## Earlier four-skill bundle proposal (superseded 2026-11-20)

Propose a **four-file general-development bundle**: Matt `codebase-design` and `diagnosing-bugs`; Poteto `principle-sequence-verifiable-units` and `principle-prove-it-works`. This samples design, diagnosis, small-task sequencing and verification while avoiding whole-collection routing, explicit security advice and mandatory human seam approval. It is deliberately not called a TDD condition. Evaluate Poteto's narrow `tdd` separately after activation feasibility; Matt's `tdd` requires a design for human confirmation before use. A later **security-specific** skill condition may be justified only with a separate rationale, pinned text, leakage review and budget-matched general-review comparator; it should not be added to this first bundle.

For each skill-enabled step session and retry, stage an immutable, hash-manifested copy of exactly these files in the disposable session's isolated home, using Codex's documented user-scope skill location `~/.agents/skills/<name>/SKILL.md` if the actual pinned CLI discovers it. The [official installation reference](https://developers.openai.com/api/reference/cli) documents that path, but discovery under this project's `--ephemeral --ignore-user-config --ignore-rules` invocation remains **unverified**. The corresponding baseline session starts with the same clean home minus the bundle. Keep skills out of the application workspace and its retained snapshots, so the starting application files remain identical across conditions. Store the source archive, license notices, manifest and staged-file hashes in researcher-only run artifacts; never mount hidden tests, benchmark-author notes, future requests or previous conversation history. If this staging path fails in the pinned harness, test a separately versioned project-local `.agents/skills/` delivery design on a disposable fixture and disclose its effect on starting files. Any adapted frontmatter or path is a new treatment artifact requiring qualification.

Keep the exact task-contract bytes and prior-request availability equal between conditions. A versioned, condition-specific wrapper may say that the skill bundle is available and should be used when applicable, but it must be stored separately from the base request and included in the condition manifest. Explicitly appending skill instructions to a developer request changes the request and confounds instruction delivery with skill use. Prefer the same generic session-launch template in both conditions, with the treatment declared by the installed files; if a wrapper is needed for reliable activation, test and report it as part of the intervention. Threat-model specifications are a different possible task-content intervention, not a substitute for skill delivery.

**Activation dry run:** on a disposable non-benchmark two-step fixture, start fresh sessions with the exact normal Codex harness, permissions and bundle location. Use a simple feature change, an ordinary bug report, a refactor and a task that should trigger none across fixture variants. Verify (1) base request bytes match across conditions, (2) only the intended four files are discoverable in the skills arm, (3) an applicable file is actually read and influences a traceable action, (4) unrelated files are not pulled in, (5) the second fresh session and an explicit retry restage identical hashes, (6) skill files stay out of application snapshots, and (7) no hidden or future materials are mounted. Record failure cases, including auto-discovery failure, Poteto frontmatter rejection, tool-call incompatibility and unintended human pauses. This checks delivery and activation, not efficacy or security. Do not use benchmark tasks for the dry run.

**Current adapter boundary:** The [host Codex adapter](../../principiis/codex.py) rejects skills in a clean `CODEX_HOME`. The [container development adapter](../../principiis/development_runtime.py) creates a disposable home and invokes `codex exec --ephemeral --ignore-user-config --ignore-rules`; it mounts only the application workspace and subscription authentication for the model session. The [manual controller](../../principiis/manual.py) assembles cumulative visible request text and retains application snapshots between fresh steps. Thus the proposed skills path needs a narrowly condition-aware provisioner and an end-to-end fixture check. These are design inferences from inspected code, not evidence that skill activation currently works. The baseline adapter behavior must stay fixed for its own condition.

**Audit fields:** application/step/attempt; base task hash and visible prior-request hashes; condition/wrapper ID and hash; upstream commit, file paths, file SHA-256, license notice and local installed path; Codex version, effective model/reasoning when exposed, tool/permission settings and fresh-session ID; skill metadata exposed, file-read events, explicit invocations, observed actions and non-use; start/end time, reported tokens, local memory scope, tool calls, tests, outcome and incomplete-attempt costs. Mark unavailable fields `unknown`. Skill activation is process evidence, not proof of causal mechanism.

## Comparison and interpretation

**Hypotheses, untested:** H1: the general bundle changes the proportion of checkpoints passing required functionality **and** applicable security properties, with direction unknown. H2: sequencing/verification may reduce later regressions while increasing elapsed time and token use. H3: design/diagnosis may improve independent maintainability evidence or repair of preauthored bug reports, but could also slow progress or produce no change. H4: a future security-specific bundle might improve security-property pass beyond a budget-matched general-review control; it could instead add cost or harm functionality. None follows from the upstream authors' claims.

Compare the same versioned application sequences, fixed task bytes and evaluator versions under baseline and proposed skill condition. Control Codex harness/version, effective model settings when exposed, normal tools, permissions, setup, task source, external fixtures, step-session reset, retry policy, compute policy and feedback. Do not reveal hidden evaluation or allow intervention instructions to become persistent baseline notes. Preserve pre/post snapshots where later review/repair is studied. Use predefined independent functional and security checks as the primary task-level conjunctive outcome; report failure and unassessable states, plus regressions. Secondary observations: independently adjudicated findings, structure/maintainability evidence with an explicit rubric, elapsed time, tokens, tool use, skill reads/use and costs separated for development/evaluation. Agent-authored visible tests are process evidence, not the independent oracle. A single run per application and dependent checkpoints cannot estimate stochastic reliability or general efficacy; treat contrasts as descriptive and avoid model-versus-harness attribution.

**Go/no-go for owner review:** proceed to a separately approved comparative run only after baseline path and oracles qualify, task/evaluator versions freeze, the non-benchmark activation dry run confirms the actual bundle, license notices and all hashes are captured, and no hidden/future context or extra permissions leak. A mismatch in discovery, unsupported dependencies, uncontrolled human gate, changed request bytes or missing cost accounting is a no-go until resolved and requalified. This note authorizes neither paid calls nor comparative execution.

## Limitations and open decisions

- This is a focused source inspection, not a systematic skill review or empirical result. Upstream `main` may move; the commits and copied byte hashes, not branch names or plugin version alone, must govern any later run.
- The first bundle mixes two authors and several mechanisms; a bundle-level difference cannot identify which skill caused it. If the pilot is promising and resources allow, isolate components in later conditions. Avoid simultaneous security skill/review additions.
- The `codebase-design` file references unbundled support documents; `diagnosing-bugs` can ask for user access; Poteto flags are Cursor-oriented. The exact Codex behavior is unresolved until the dry run. No external scripts, packages or model services are required by the four selected `SKILL.md` bodies, but their suggested actions can use normal tools and consume resources.
- The owner has since chosen the custom workflow direction described in [the current design](../DEVELOPMENT_SKILL_CONDITION.md). Exact skill and invocation bytes, delivery qualification, run order and comparative launch remain open. Draft benchmark requests and evaluator status can change before freezing.
